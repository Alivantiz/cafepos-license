# Панель подписок iMag (Cloudflare Pages)

Отдельный Pages-проект (не трогает `imag-hall-view`). Режим **Advanced
mode**: `public/_worker.js` — бэкенд, он обрабатывает `/api/*`, а всё
остальное отдаёт из собранного интерфейса через `env.ASSETS`. Сервис-role
ключ Supabase живёт переменной окружения Pages-проекта (server-side, в
браузер не попадает). Вход по паролю (`PANEL_PASSWORD`), пароль
запоминается в браузере.

## Сборка

Интерфейс — Vite + React в `panel/src`. Воркер лежит в `panel/public/`,
откуда Vite кладёт его в корень `dist/` — этого требует Advanced mode.

Выкладывает **не** гит-интеграция Cloudflare, а workflow
`.github/workflows/deploy-panel.yml`: `npm ci` → `node panel/test.js` →
`npm run build` → `wrangler pages deploy dist`. Настройки сборки в панели
Cloudflare при этом ни на что не влияют — трогать их не нужно.

Запускается сам при изменениях в `panel/**`; вручную — кнопкой Run workflow
(например после правки самого workflow: фильтр `paths` такие изменения
не ловит).

Локально: `npm install && npm run dev`. Проверки: `node test.js` —
маршруты воркера, разбор ответов облака, арифметика денежных свёрток.

## Экраны

**Сводка** — что требует внимания сегодня: платящие, на пробе, истекающие,
молчащие, оборот парка, общий график и список с причинами. Молчащие
считаются по последней ПРОДАЖЕ, а не по последней связи: касса может
исправно звонить за лицензией и не пробить ни чека — именно это и значит,
что клиент отваливается.

**Клиенты** — строка на заведение: статус, выручка за неделю, динамика к
прошлой, миниграфик, средний чек, последняя продажа, число касс. Поиск,
фильтры, сортировка. **Выпустить** заводит строку в `licenses`, её id и
есть код активации для кассы.

**Карточка клиента** — всё про одно заведение: выручка за 7 и 30 дней,
средний чек, график по дням, данные лицензии, заметка, история продлений,
**Продлить** (от сегодня или текущего срока — что позже, `revoked`
снимается) с готовым текстом клиенту, **Отозвать/Вернуть**, **Скрыть**,
**Отложить** (до даты не попадает в «требует внимания», но остаётся в
списке и в подсчётах).

Сводка считает СВОИ деньги, а не чужие: «получено за 30 дней» — сумма
записанных продлений, «ожидается за 30 дней» — цены тех, у кого лицензия
истекает в ближайший месяц. Цена (`licenses.price`) — за ОДНО продление,
не «в месяц»: кто-то платит помесячно, кто-то за год.

Цифры берутся из `usage_daily`/`usage_state` — дневных итогов, которые
касса шлёт по каналу лицензии (`/status`, `/trial`). Клиент на версии без
этой телеметрии честно помечен «касса на старой версии», а не показан
нулями. Пока SQL с этими таблицами не выполнен, панель работает без цифр,
а не отдаёт ошибку.

Вкладка **«Заявки»** — заявки на активацию (`activation_requests`): касса
присылает их сама функцией `request-activation`, поэтому код компьютера у
клиента спрашивать не нужно. **Одобрить** заводит лицензию с этим
`machine_id`, и касса забирает её сама (функция `claim`) — отдельного
«выключателя» нет, лицензия и есть одобрение. Статус заявки на «одобрено»
переводит именно `claim`, в момент, когда касса реально пришла: пока этого
не случилось, в списке видно «ждёт решения», а не ложное «готово».

Вкладка **«Триалы»** — воронка ДО оплаты: кто поставил кассу и ещё не
заплатил. Касса без лицензии раз в сутки сообщает состояние (функция `trial`
→ таблица `trials`), но посмотреть это было негде — ни вкладки, ни отчёта,
только SQL руками. Строки разобраны по состояниям, потому что это разные
разговоры с клиентом: **«истёк, но кассу открывают»** (самые тёплые —
продукт нужен, денег не отдали), **горящие** (осталось ≤3 дней), идущие,
**тихие** (молчат ≥3 дней) и мёртвые. Бейджем считаются только первые две
группы: счётчик должен звать к действию, а не показывать объём базы.

Вкладка **«Облако»** — живы ли сами облачные функции. Панель, как и вся
админка, читает только таблицы, а касса разговаривает с функциями: если
функция не выложена, таблица просто остаётся пустой, и со стороны это
неотличимо от «клиентов нет». Так уже было с `trial` — установки демо не
записывались, и это читалось как «демо никто не ставит». Каждая из шести
функций опрашивается вживую (GET отдаёт версию, данных и ключей не отдаёт);
отдельно видно случаи, когда функция отвечает, но работать не может — нет
таблицы или не задан `LICENSE_PRIVATE_KEY`. Счётчик неработающих виден на
вкладке сразу после входа, заходить внутрь не нужно.

Вкладки **«База»** (правка произвольных таблиц) в панели нет — прежний
абзац описывал незаконченную задумку; смотреть таблицы можно в Supabase
Table Editor.

Структура:
```
license-admin/panel/
  public/_worker.js   ← вся панель (страница + API), Pages Advanced mode
  README.md
```

## Деплой нового Pages-проекта (один раз)

Тем же способом, что `imag-hall-view`. Через CLI:

```bash
cd license-admin/panel
npx wrangler pages project create imag-license-panel   # создать проект (один раз)
npx wrangler pages deploy public --project-name imag-license-panel
```

Либо через дашборд: **Cloudflare → Workers & Pages → Create → Pages →
Direct upload**, имя `imag-license-panel`, загрузить папку `public`.

## Переменные окружения (обязательно)

Dashboard проекта → **Settings → Environment variables → Production** (или
`npx wrangler pages secret put …`). Задать:

- `SUPABASE_URL` — адрес проекта лицензий, `https://<ref>.supabase.co`
  (тот же, куда стучится касса за активацией; ref у тебя `uvuzotcilselezjwrpmb`).
- `SUPABASE_SERVICE_ROLE_KEY` — service_role ключ того же проекта
  (Supabase → Settings → API). **Секрет**, шифруется.
- `PANEL_PASSWORD` — пароль для входа в панель (придумай сам).
- `OWNER_KASPI_PHONE` — необязательно, номер для текста клиенту.

После задания переменных — передеплой (`wrangler pages deploy public` ещё
раз или Retry deployment в дашборде), чтобы они применились.

Адрес будет вида `https://imag-license-panel.pages.dev` — открываешь,
вводишь `PANEL_PASSWORD`.

## Обновление

Правишь `public/_worker.js` → снова `npx wrangler pages deploy public
--project-name imag-license-panel`. Переменные сохраняются.

## Обучаемое сопоставление названий (накладные, опечатки, сокращения)

Однократная настройка: выполнить `sql/mon_matching.sql` в SQL Editor проекта
`imag_monitoring`. Скрипт создаёт:

- `mon_norm_name(text)` — нормализация («Мол.,3.2% (1л)» → «мол 3 2 1л»);
- таблицу `mon_aliases` — выученные пары «грязное название → штрихкод»;
- `mon_match_product(q, max_results)` — подбор карточки: сперва точный алиас
  (`match_kind='alias'`, score=1), иначе топ похожих по триграммам pg_trgm
  (`match_kind='fuzzy'`, score 0..1). Вызов:
  `POST /rest/v1/rpc/mon_match_product {"q":"мол 3.2 1л"}`;
- `mon_learn_alias(raw_name, p_barcode, p_source, p_by)` — обучение:
  подтверждённое сопоставление запоминается (upsert), прямых прав записи в
  `mon_aliases` у anon нет (security definer).

Круг обучения для разбора накладных (делается на стороне кассы/ИИ):
строка накладной → `mon_match_product` → если алиас, берём сразу; если fuzzy —
человек/ИИ подтверждает → `mon_learn_alias` → в следующий раз строка матчится
мгновенно. В панели при модерации кнопка **≈** у заявки показывает похожие
карточки каталога (`/api/catalog/similar`) — видно дубли до одобрения; совпад
по штрихкоду подсвечивается «тот же штрихкод!».

Отдельно: `sql/mon_heartbeat_rls_fix.sql` — RLS-политики для
`mon_heartbeat` (лечит 401/42501 на POST heartbeat с касс).

## Keepalive (чтобы Supabase не заснул)

Бесплатные Supabase-проекты засыпают после 7 дней без API-активности.
Страховка двойная:

- при входе в панель сразу грузится очередь модерации штрихкодов (бейдж
  «N» на вкладке) — активность получают **оба** проекта, а не только лицензии;
- `GET /api/keepalive` панели делает лёгкий запрос в оба проекта. Endpoint
  без пароля, наружу отдаёт только `{ok, licenses, monitor}`. Его дёргают
  два независимых пинга:
  - **Worker `imag-keepalive`** (`keepalive-worker/`, cron 15:47 UTC) —
    основной: cron-триггер Cloudflare не отключается за неактивность,
    работает пока жив аккаунт. Деплоится workflow «Деплой keepalive-воркера»
    при изменении `keepalive-worker/**`.
  - workflow «Автопинг Supabase» (cron 03:17 UTC) — дублирующий; GitHub
    ставит расписания на паузу после ~60 дней без коммитов. Адрес панели по
    умолчанию `https://imag-license-panel.pages.dev`, переопределяется
    repo-переменной `PANEL_URL` (Settings → Variables).

## Приложение на телефоне и уведомления

Панель — PWA: `Поделиться → На экран «Домой»`, дальше это отдельная иконка
без адресной строки. На iOS это не косметика: push получает **только**
приложение с домашнего экрана, закладка Safari — никогда.

Кнопка **«Уведомления»** внизу меню включает подписку и умеет прислать
проверочное. Приходят три вещи, остальное — очередь, которая подождёт:

- касса сообщила о поломке (SOS за последние сутки);
- новая заявка на активацию;
- у клиента заканчивается подписка (≤3 дней).

Как это устроено: пара ключей VAPID генерируется панелью при первой подписке
и лежит в `push_state` — отдельного секрета в Cloudflare заводить не надо.
Подписки браузеров — в `push_subs`, мёртвые (404/410) вычищаются при первой
же неудачной отправке. Шифрование тела — RFC 8291 руками (`_worker.js`),
потому что в Advanced mode воркер это один файл без сборщика; проверяется в
`test.js` расшифровкой, играя за браузер.

Будит телефон не панель, а cron-воркер `imag-keepalive`: раз в четверть часа
дёргает `GET /api/push/check`. Endpoint без пароля, как и `/api/keepalive` —
данных наружу не отдаёт, а дважды одно и то же не пришлёт: ключ события
пишется в `push_state` с `resolution=ignore-duplicates`. Если разом
набралось больше трёх событий (первая проверка после установки), уходит одно
сводное уведомление вместо пяти.

**Нужен SQL**: таблицы `push_subs` и `push_state` — в конце
`license-server/supabase/schema.sql` репозитория iMag. Без них кнопка
«Включить» честно скажет, что таблиц нет.

## Ограничения (осознанные)

- **Отзыв — только отсюда.** Касса ловит `revoked` через `/status` при
  выходе в интернет. Workflow «Отозвать» удалён: он собирал подписанный
  `crl.json`, но кассы этот список не скачивают ни разу — адрес берётся из
  `app_settings.crl_url`, а этот ключ нигде не засеян и не редактируется.
  Кнопка нажималась, лог был зелёный, лицензия продолжала работать.
- **Выпуск из панели** заводит строку в `licenses` под активацию по коду
  (клиент вводит id на кассе, `.lic` подписывает функция `activate`).
  Готовый `.lic`-файл — workflow «Выпустить лицензию файлом», только для
  кассы без интернета: подпись требует `LICENSE_PRIVATE_KEY`, которого у
  панели нет и не должно быть. Строку в `licenses` тот workflow теперь
  заводит сам, поэтому такая лицензия видна здесь и управляется как все.
- Пароль — простое сравнение. Для панели одного владельца достаточно;
  если нужен вход по коду на e-mail — поверх включается Cloudflare Access,
  без правок кода.
- Автовыставления счетов нет (у Kaspi нет публичного API) — панель даёт
  готовый текст со счётом после «Продлить»/«Выпустить».
